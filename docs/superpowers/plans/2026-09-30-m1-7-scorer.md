# M1-7: Scorer, coverage, actions, assumptions
m1-7-scorer · plan-gated · Notion: (card id not supplied)

## Goal and scope
Turn one date's M1-6 findings into a verdict, a risk score, an opportunity score, a coverage value and a breakdown (spec §2.2). Rank the candidate dates within coverage buckets. Pick up to 3 dated actions (§2.3). Resolve the assumptions from organizer input or the genre profile (§2.3). This is code only: no endpoint, no persistence, no Spring beans. M1-8 wires it and writes `date_check_date` (V162).
Out of scope: web findings (M2), templates and i18n (M3), the assumption PATCH (M1-8).

## Ordered steps

1. Add the three components to `DateCheckInput`, keeping the compact constructor's rules. `communities` stays null when not provided, so null means empty input and an explicit `[]` is the organizer's own value, the same rule as `knownEvents`. If there are more than 5 constructor callers, add a test-only builder instead of editing each one.
2. `Scorer`:
   - `points = min(maxPointsPerFinding, strength*weight)`, counted only for FOUND rows.
   - `risk = min(10, sum of RISK points)` and `opp = min(10, sum of OPPORTUNITY points)`. The two sums are separate, so opportunities never offset risk.
   - Breakdown: one line per FOUND row, points descending (ties by questionId). The lines keep their uncapped sum; the UI shows the cap.
   - Coverage: applicable = the distinct questionIds among the findings that are in `starIds`. RuleEngine emits only rows that apply, and `not_checked` rows count as applicable. An id counts as checked when any of its rows is FOUND or CLEAR. `coverage = checked/applicable`, scale 3, `RoundingMode.DOWN`. With zero applicable ids, coverage is 0.
   - Verdict, in this order:
     1. any stopFactor gives MOVE;
     2. `risk >= moveMinRisk` gives MOVE;
     3. `coverage < minCoverage` (compared as BigDecimal) gives NOT_ENOUGH_DATA;
     4. `risk >= adjustMinRisk` gives ADJUST;
     5. otherwise GOOD.
   - Why steps 1 and 2 come before coverage: a stop factor is a confirmed structured or internal fact (M1-6 guarantees no web or organizer stop factors). Unchecked questions can only add risk, so MOVE is a floor no matter what coverage is missing. Low coverage therefore only ever blocks GOOD or ADJUST, and never hides a confirmed MOVE.
   - `starIds` for the bank overload: ids with `star == true` on any of their rows.
3. `Ranker`:
   - Bucket: HIGH when coverage ≥ 0.800; MID when coverage is 0.600 up to (not including) 0.800; otherwise NONE.
   - NONE and NOT_ENOUGH_DATA dates get `rank = null`.
   - Within each bucket, sort by risk ascending, then opp descending, then leadDays descending, then date ascending (deterministic). Ranks are 1..n per bucket.
   - Buckets are never compared with each other; M3 groups them.
4. `ActionPicker`:
   - Take the FOUND findings in `Scorer.points` order, descending. Look up the question by (id, sourceKind); if there's no match, throw `IllegalArgumentException`.
   - Keep the actions whose `when == finding.kind`. Set `dueDate = eventDate.minusDays(dueDays)` and drop any with `dueDate.isBefore(today)`; the due date equal to today is kept.
   - Dedupe by key; the first hit wins, so it carries the highest points. Then limit to 3. Past-due actions are dropped before the cap so they never take a slot.
   - `params` = the finding's `facts`.
5. `AssumptionResolver`:
   - Always returns one entry per Field, in enum order. The organizer's value wins, with `source ORGANIZER`, `estimate false` and a null url. Otherwise the profile's `ProfileField` is used, with `source PROFILE` and its `estimate` / `sourcedUrl`.
   - Price: the organizer's `priceMinor` is used as-is; the profile's `typicalPriceEur` range is converted to minor units (×100). Everything is in one unit.
   - If the profile is null, or a profile field is null, and the organizer left that field empty, the Field is omitted. Nothing is ever invented.
6. Write the tests below and run the verification command.

## Risks
- **Upstream unmerged:** the M1-6 signatures come from its plan only. Step 0 re-verifies them. If M1-6 has changed, adapt the M1-7 code to it rather than editing M1-6 again.
- **Verdict order differs from the spec's listing:** MOVE beats NOT_ENOUGH_DATA. The argument (monotone lower bound) is in step 2 and needs Ivan's confirmation (open question 1).
- **Coverage headroom:** with 3.2 and 5.1 not_checked until M1-4b, FR peaks at 0.8 (8/10) and a UA city with no school data sits at about 0.75. `not_enough_data` bites only where two or more further star checks are missing. Revisit when M2 adds the web star questions (bank v3).
- **Per-bucket ranks:** two dates can both be rank 1. M3 must show the bucket beside the rank.
- **Price currency:** `priceMinor` has no currency and the profile is in EUR. This is wrong for UAH organizers (open question 3).
- **Size:** about 14 files, one concern, no split.

## Decisions (main session, 2026-09-30)
